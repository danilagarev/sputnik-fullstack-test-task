# Файлообменник — решение тестового задания

Исходный MVP: загрузка файлов, проверка на подозрительный контент, лента алертов.
В работе три задачи из задания — рефакторинг бэкенда, неочевидная оптимизация,
разбиение фронтенда на слои — плюс исправление багов, найденных по пути.
Бизнес-логика (правила проверки, статусы, тексты алертов) не менялась.

## Запуск

```bash
docker compose -f docker-compose.dev.yml up -d --build
docker exec -it backend alembic upgrade head
```

* Фронт: http://localhost:3000/test
* Бэк: http://localhost:8000/docs

Конфигурация — в `.env.dev`; секретов в репозитории нет.

Браузер ходит в API напрямую, поэтому его адрес — переменная фронтенда
`NEXT_PUBLIC_API_URL` со значением по умолчанию `http://localhost:8000`. Если
стек поднят не на той машине, с которой открываете страницу, задайте её при
сборке фронта и добавьте свой origin в `CORS_ORIGINS`.

### Проверки

```bash
cd backend  && uv sync && uv run ruff check . && uv run mypy && uv run pytest
cd frontend && npm install && npm run lint && npm run typecheck && npm test
```

Интеграционные тесты бэкенда поднимают собственную базу; нужен запущенный
Postgres (`POSTGRES_HOST=127.0.0.1 PGPORT=5433` для стенда из compose).

## Архитектура бэкенда

Было: `app.py` (роуты + HTTP-ошибки), `service.py` (движок БД, файловая система,
бизнес-правила, `HTTPException`), `tasks.py` (второй движок БД, свой цикл
событий, снова бизнес-правила). Движки, пул и создание каталога хранилища
возникали как побочный эффект импорта, поэтому модуль нельзя было импортировать
без настроенного окружения, а в тестах приходилось патчить глобальные объекты.

Стало — слои с зависимостями строго внутрь:

```
api/          роутеры, DI, преобразование доменных ошибок в HTTP
services/     бизнес-логика: приём файла, пайплайн обработки, правила скана
repositories/ все запросы к таблицам
storage/      файловое хранилище за узким интерфейсом
domain/       модели, статусы, интерфейс проб
workers/      Celery: конфиг, публикация, задача
core/         настройки, движок и сессии, доменные ошибки
```

Что это даёт по пунктам:

* **Сервис не знает ни про FastAPI, ни про Celery.** Он бросает доменные ошибки
  (`FileNotFound`, `EmptyUpload`, …), а в статусы их переводит единственное
  место — `api/errors.py`. Поэтому один и тот же код обслуживает HTTP-запрос и
  фоновую задачу: раньше воркер импортировал модуль, который бросает
  `HTTPException`.
* **Сессия приходит через `Depends`.** Границы транзакции видны, соединение
  возвращается в пул, а в тестах хранилище и очередь подменяются через
  `dependency_overrides` вместо monkeypatch по трём модулям.
* **Один движок, создаётся лениво.** Импорт пакета больше не открывает пул и не
  требует переменных окружения; воркер создаёт свой цикл событий после fork —
  пул asyncpg принадлежит тому циклу, который его первым коснулся.
* **Настройки валидируются.** Раньше отсутствующая переменная превращалась в
  строку `"None"` внутри DSN и всплывала ошибкой соединения на первом запросе.

## Оптимизация

`create_file` читал тело запроса целиком в память (`await upload_file.read()`),
а потом задача `extract_file_metadata` открывала тот же файл с диска и читала
его второй раз, чтобы посчитать строки или страницы PDF.

Теперь файл проходится **ровно один раз**: тот же поток, что пишется на диск,
по пути скармливается пробам (`TextProbe`, `PdfPageProbe`), и посчитанные
метрики едут в воркер в теле задачи. Память — один чанк, а не весь файл; чтений
файла — одно вместо двух.

Побочный эффект того же разбора: цепочка из трёх задач (скан → метаданные →
алерт), где каждая публиковала следующую и перечитывала ту же строку в своей
сессии, свернулась в одну. Шаги строго последовательны и делят все входные
данные, так что разделение стоило трёх обращений к брокеру и трёх транзакций и
не давало ничего.

Запись на диск вынесена в `asyncio.to_thread`: файловый ввод-вывод отпускает
GIL, и на цикле событий гигабайтная загрузка блокировала бы все остальные
запросы. Пробы работают в том же потоке, GIL держат, поэтому чанк ограничен
`upload_chunk_bytes` (1 МБ) — это плата за то, что метрики считаются на лету.

## Фронтенд: слои

`page.tsx` на 367 строк содержал типы, форматтеры, `fetch` с зашитым
`http://localhost:8000`, всё состояние и всю разметку. Разложено по FSD:

```
app/       композиция страницы и провайдеры
widgets/   dashboard (единственное место, знающее обе сущности), таблицы, шапка
features/  загрузка, переименование, удаление файла
entities/  file и alert: тип, производные состояния, запросы
shared/    http-клиент, ключи кэша, конфиг, форматтеры
```

Правило зависимостей — сверху вниз; слайсы одного слоя друг друга не импортируют,
поэтому «идёт ли обработка» — параметр `useAlerts`, а не подглядывание в кэш
соседней сущности: связывает их виджет `Dashboard`, которому это положено.

Данные — на React Query: опрос идёт, только пока хоть один файл не в терминальном
статусе, и прекращается сам. Раньше статус «uploaded» висел до ручного
«Обновить», а любое обновление подменяло всю таблицу спиннером.

## Исправленные баги

| | |
|---|---|
| Удаление обработанного файла падало | у `alerts.file_id` не было `ON DELETE CASCADE`, а обработанный файл всегда владеет алертом |
| Файл мог навсегда застрять в `processing` | любая ошибка теперь терминальна: статус `failed` и критический алерт |
| Повторная доставка задачи дублировала алерт | строка переводится `uploaded → processing` одним условным `UPDATE`, второй раз он не проходит |
| PDF всегда «одна страница» | искали `/Type /Page` с пробелом, чего не пишет ни один генератор; заодно `/Type/Pages` (дерево страниц) больше не считается |
| Длинное имя или заголовок → 500 | обе колонки `String(255)`, проверка перенесена в сервис, ответ 400 |
| Пустой заголовок принимался | браузер обрезал ввод, любой другой клиент — нет |
| Размер файла обрезался на 2.1 ГБ | `Integer` → `BigInteger` |
| Точка в имени файла считалась расширением | «Отчёт за 2026.09 итог» уезжал на диск с суффиксом `.09 итог` |
| Списки возвращали всю таблицу | у `/files` и `/alerts` есть `limit` с потолком |
| Размер загрузки ничем не ограничен | лимит проверяется дважды: по заявленному `Content-Length` — до того, как парсер multipart сложит тело во временный файл, и счётчиком байтов при записи — для запросов без длины |
| Значок проверки был зелёным до скана | цвет брался из `requires_attention`, который до проверки `false` |
| Стек не поднимался с чистого чекаута | том Postgres монтировался мимо `PGDATA`, а хранилище было недоступно непривилегированному процессу |

## Тесты

* `backend/tests/unit` — правила скана и потоковые пробы: без БД, диска и цикла
  событий. Пробы проверяются на неудобных границах чанков, включая CRLF на стыке
  и многобайтные символы, — потокового бага не видно в сквозном тесте.
* `backend/tests/integration` — поведение API и пайплайна через публичный
  контракт: коды ответов, имена полей, порядок. Пайплайн проверяется через
  «загрузить и прогнать очередь», а не через вызов конкретных задач, — тесты не
  зависят от того, из скольких задач он состоит.
* `frontend/tests` — форматтеры, производные состояния сущности, обе таблицы,
  диалог загрузки и действия над файлом.

## Осознанно за рамками

* **Аутентификация и права.** В задании их нет; добавлять их — менять продукт.
* **Sweeper для «зависших» строк.** Два узких места задокументированы в коде:
  упавшая публикация в брокер оставляет файл в `uploaded`, убитый воркер — в
  `processing`. Лечится периодической задачей или outbox-таблицей; и то и другое
  — отдельная инфраструктура, а не часть рефакторинга.
* **Продакшн-обвязка** (nginx, CI, отдельный compose) — вне задания.
* **Остатки шаблона `with-docker`** — `frontend/README.md` (документирует
  `create-next-app`, а не этот проект), `app.json` (дескриптор Cloud Run, ничем
  не читается) и `Dockerfile.bun` (требует `bun.lock`, которого в репозитории
  нет, — путь сборки нерабочий). Не трогал: это файлы исходного репозитория, их
  судьба — решение владельца.
* **Пагинация курсором.** Потолок `limit` закрывает проблему «отдаём всю
  таблицу»; курсор нужен, когда список реально длинный, и тянет за собой
  контракт ответа и подгрузку на клиенте.
